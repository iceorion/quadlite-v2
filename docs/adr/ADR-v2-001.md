## 决策

### D1（沿用）B0 保持 0 行产品代码，只交付工程骨架与可机器验证的检查链

- 交付：`Directory.Build.props`、三个 SDK 风格 csproj、`app.manifest`（PerMonitorV2）、`build.ps1`、`.gitignore`、`tools/` 下的检查脚本与夹具、CI workflow、证据闭环文档。
- `src/` 下不写产品源码；`QuadLite.Tests` 的 C# 零依赖 runner 与 exe 形态 `--selftest` 随 B1 / B7 加入。
- **偏差显式记录**：§8.4 要求「每批结束时应用必须可启动」，B0 是唯一以检查链 runner（`tools/run_tests.py`）为可运行形态的骨架批次，不宣称应用已可启动，构建与出包标「未验证」。B1 起恢复该判据。
- 理由：docs-first 路线的第一批不该顺手写功能代码；B0 的价值是把「门卡能红、需求可追踪、合规可扫描」这条链先立起来并实测过，再让 B1 的纯函数层落在可验证的地基上。

### D2（修订）静态检查链改用 Python 3 标准库，门卡名不变

- 规格 §4.2 与附录 C 的脚本名由 `tools/check-boundaries.ps1` / `tools/check-trace.ps1` 修订为 `tools/check_boundaries.py` / `tools/check_trace.py`，并新增 `tools/run_tests.py`、`tools/check_open_source.py`。
- 理由：本机执行策略禁止运行 `.ps1` 脚本，且本机无法确认 net48 构建工具链；而门卡必须能在本机与 CI 重跑、能做负向对照，否则「改坏必红」无从验证。改用 Python 3 标准库后零第三方依赖、CI 直接可用。
- 不变的部分：产品运行时仍是 net48 + WPF + C# 5 语法子集（DD-01 / C-01 / C-04）；`build.ps1` 仍是 PowerShell（构建与出包属 Windows 专属）；门卡名 `check-boundaries` / `check-trace` 不变；C-03「环境解绑不得改变产品行为」不受影响。

### D3（沿用）O-01 / O-05 / O-06 按默认值执行

- O-01：不统一 shell 互操作，B2 与 B5 各用成熟 COM 绑定 + 参数硬校验。
- O-05：保留 3 窗格（1/2/3/4 四档布局）。
- O-06：列头筛选与显示开关全部进首版。
- 规格 §11 已加「确认状态」列；O-02 / O-03 / O-04 仍按默认执行。

### D4（新增）账本 `head_sha` 用回填提交写入

- 一个提交无法在同一提交里写下自己的 SHA。故每批的功能提交先落地，账本行在紧随其后的回填提交中写入该提交的 SHA；回填提交只改 `docs/run-ledger.md`，不产生新批次行。
- 复核：`git cat-file -e <head_sha>` 与 `git show -s --format=%s <head_sha>` 对应到该批提交信息。

### D5（沿用）未跑过的一律写「未验证」

- B0 未验证项集中登记在 `docs/negative-controls.md`：同手感、零写入三段取证、高 DPI 四档、危险判级矩阵、B5 的 `GetCommandString` 实测、MSBuild 构建、单文件出包、exe 形态 `--selftest`。
- 不用「没报错」冒充「没被拦」，不写「全绿」式结论。
- 同日补充：CI 首次实跑已通过（run `42013589562`，head `96a5fa4`，四个门卡步骤全 `success`），故 CI 由「未验证」转为「实测」；上列其余未验证项不受影响，因为 CI 未包含 .NET 构建与出包。
