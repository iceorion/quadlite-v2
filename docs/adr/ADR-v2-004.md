## 决策

### D1（沿用）规格与待决项不动
`design-v2.md` 保持 v1.2；O-01 / O-05 / O-06 按默认值执行；窗格布局的两种分割线方案仍在讨论中、未拍板。B2 不触碰布局，也不因本批次改动规格。

### D2（新增）三层证据，互不冒充
| 层 | 内容 | 验证方式 | 结论 |
|---|---|---|---|
| L1 编排（Core） | 端口契约、`OperationCoordinator`、`UndoStack`、命名与冲突、自操作抑制、去抖节流、剪贴板数据、CLI、便携根、结果分类 | CI 以 `/langversion:5` 编译并运行零依赖 C# runner | 算法与编排逻辑实测 |
| L3 适配器（Fs） | `AtomicFile` / `FsWatchService` / `DirSource` / `FileClipboard` / `ShellFileOperator` | CI 编译成 library（只编译、不运行）+ `check_fs_specs.py` 静态契约 | 结构与语法可判，运行期行为未验证 |
| 真实系统能力 | `IFileOperation` 搬运、系统剪贴板互通、watcher 实际订阅、WPF 应用构建与出包 | 发布线 H1–H6 / B3 外壳 / B7 出包 | **未实现 / 未验证** |

本机安全策略禁止执行系统 C# 编译器，故本机只跑 Python 静态门卡；不把静态绿写成算法跑通，也不把 CI 编译写成功能可用。

### D3（新增）端口契约冻结，真实 shell 调用点隔离
Core 新增 `IFileOperator` / `IClipboard` / `IShellVerbs` / `IFsWatch` / `IDirSource` / `IDangerPolicy` / `IPreflight` / `IClock` / `IRefreshSink` 等端口，签名与 §6.1 一致；`ShellFileOperator` 只做请求校验与结构化结果回传，真实搬运注入 `IShellTransport`。

**不手写 COM 接口布局**：§5.2 参数纪律明文要求「COM 声明使用成熟绑定，不手写 vtable」，而手写 vtable 顺序正是 v1 原生菜单崩溃链路的成因之一；O-01 也未指定具体成熟绑定。因此本批不声明 `IFileOperation` 布局、不调用真实 shell。成熟绑定选定后由一条新 ADR 接入 `IShellTransport`，端口与编排层无需改动。`check_fs_specs.py` 把「出现 `ComImport` / `InterfaceType` / `Guid` 声明」判红，防止后续有人抄近路。

### D4（新增）判级经端口注入，单点仍在 SafetyGuard
`OperationCoordinator` 只消费 `IDangerPolicy.Decide` 的 `GuardVerdict`，不自造判级表；判级矩阵仍只在 `SafetyGuard.cs` 一处（`check_boundaries.py` INV-05 保持绿）。真实绑定留到 B3（App 外壳尚未开工），本批由 `FakeDangerPolicy` 覆盖，因此没有新增第二套判级逻辑。

### D5（新增）门卡与负向对照
新增 `tools/check_fs_specs.py`（适配器齐备 / 端口绑定 / 禁止手写 COM / shell 隔离 / C# 5 语法）；扩展 `check_core_specs.py`（Core 类型 13 → 23、门卡组 14 → 21、枚举 14 → 19）；`run_tests.py` 增加 1 组正向与 4 类负向对照（删编排类型、删 B2 门卡组、删适配器、注入手写 COM），共 25 组 / 19 条负向。CI 增加 `check-fs-specs` 与 `csharp-fs-compile` 两步。

### D6（偏差，如实登记）§8.1 B2 未交付完的部分
- 「接管冲突与进度 UI」属 B3 外壳的非模态面板，B2 只冻结 `PreflightResult` 数据契约，未实现 UI。
- 「`ShellFileOperator` 经真实 `IFileOperation` 搬运」未实现，见 D3。
- 「`IFileOperationProgressSink` 的 `PostDeleteItem` 取得回收站真实路径」未实现；`OpItem.ActualTarget` 由端口回传，撤销栈按「拿不到真实位置不入栈」判定，链路已通但真实取值未验证。
- **本批不等于「能搬运文件了」**，也不等于「应用可启动」。B2 交付的是多窗口编排的可验证内核 + 冻结的端口契约。

## 理由

1. B2 的核心价值是「多窗口资源管理」的编排正确性（串行闸门、跨窗格撤销、一次刷新、结果不吞错误），这些全是纯逻辑，完全可以在零 I/O 条件下 100% 单测；把不可验证的 shell 调用混进来只会稀释证据。
2. 先冻结端口再接真实适配器，返工面最小：将来换成熟 COM 绑定只动 `IShellTransport` 的实现，编排层、门卡、Fake 全不动。
3. 与 B0/B1 的证据纪律一致：每层只宣称自己实测过的东西，未验证项集中登记在 `docs/negative-controls.md` 与账本。
