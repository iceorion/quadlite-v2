- **状态**：生效（2026-11-05）
- **批次**：B3（L4 外壳）
- **关联**：`design-v2.md` §4.1 / §5.8 / §6.4 / §7.1 / §8.1 / §8.2 / 附录 C；`ADR-v2-001` D3/D5、`ADR-v2-002` D5、`ADR-v2-004` D1/D2/D6
- **编号说明**：`ADR-v2-003` 曾用于一次被撤回的布局改版（提交 `e23f8d6` → revert `d24bb44`），编号跳过、不再复用。

## 决策

### D1（沿用）规格与布局决策不动
`design-v2.md` 保持 **v1.2**：四档 `LayoutMode {One,Two,Three,Four}`、3 窗格 `RowSpan=3`、O-05 保留 3 窗格。用户提出的「两种分割线拓扑 + 折叠组合 / 拖动自定义窗格」**仍在讨论中、未拍板**，本批既不采纳也不否定，规格不改一个字，O-05 状态不变。B3 按规格既有的四档实现，是把「已定稿的规格」变成可验证代码，不是替用户就新方案下结论。

`check_shell_specs.py` 增加一条「规格与实现一致」门卡：规格中的四档声明或待决项确认状态被改动即判红，提醒实现与门卡同步修改。这是对上一轮「把探讨当定论写进规格」事件的制度化防护。

### D2（沿用 B1/B2 的证据分层）B3 交付可验证内核，不冒充可运行应用
| 层 | 内容 | 验证方式 | 结论 |
|---|---|---|---|
| L0 / 编排（Core） | B3 新增 9 个零 I/O 类型：布局槽位与跨度、分隔条数学、窗格状态、标签组、导航、地址栏、书签、会话、此电脑层 | CI 以 `/langversion:5` 编译并运行零依赖 C# runner（27 组） | 布局 / 导航 / 会话算法实测 |
| L4 状态内核（App） | `ShellState` / `ShellCommands`：只读 Core 结果，装配外壳状态 | CI 编成 library（只编译、不运行）+ `check_shell_specs.py` 静态契约 | 结构与语法可判，运行期行为未验证 |
| 真实表现层 | WPF 窗口 / XAML / 消息循环 / 事件绑定 / 系统原生菜单 / 冲突与进度面板 / 可编辑地址栏与标签拖动 UI / 此电脑层真实 `IDirSource` 合成 / 会话原子写 | B3 后续批次、B5、B7、发布线 | **未实现 / 未验证** |

本机安全策略禁止执行系统 C# 编译器，故本机只跑 Python 静态门卡；不把静态绿写成算法跑通，也不把 CI 编译写成应用可用。

### D3（新增）四档布局按规格落地，判据逐条可断言
- `LayoutMath`：1/2/3/4 档槽位表（3x3 逻辑网格）、3 窗格主窗格 `RowSpan=3`、五档窗口钉点、全局唯一活动窗格（只接受显式 paneId，不从焦点控件推断）、布局切换不销毁 `PaneState` 对象。
- `SplitMath`：比例按「相对均分偏移」存储并跨窗口尺寸保持、折叠 0/1 且不另存可见性布尔、24px 吸附、折前比例恢复、连线数、折叠不改变窗格对象数量。
- `PaneSet` 固定 4 个窗格对象，四档布局复用同一组引用；`PaneState` 承载每窗格独立的路径 / generation / 滚动锚 / 视图 / 列宽偏好 / 筛选 / 加载状态。

### D4（新增）门卡与负向对照
C# runner 由 21 组扩到 **27 组**：新增 `layout-*`（七条判据 + 三条负向，含 3 窗格退化成 4 窗格落位）、`split-*`（九条 + 五条负向）、`tab-*`（九条）、`nav-*`、`bookmark-*`、`session-*`；`path-*` 扩到地址栏输入规范化、结构化原因码与驱动器下拉。`check_core_specs.py` 的 Core 类型 23 → 32、门卡组 21 → 27、枚举 19 → 25。

`run_tests.py` 由 25 组扩到 **32 组 / 25 条负向对照**，新增 1 组 `check-shell-specs` 正向与 6 类外壳静态契约负向对照（删布局类型 / 删 B3 门卡组 / 3 窗格退化 / 删 App 骨架 / App 层注入 `System.IO` / 注入 C# 6 语法），逐条实测变红。

### D5（新增）CI 两步
`check-shell-specs`（B3 静态契约）与 `csharp-app-compile`（Core + App 编成 library，只编译不运行）。后者沿用 `csc.exe /langversion:5 /r:System.dll /r:System.Core.dll`，**不引用呈现框架程序集**：本批 App 骨架刻意不依赖 WPF 类型，从而不引入一条本机无法验证的 MSBuild 链路。

### D6（偏差，如实登记）§8.1 B3 未交付完的部分
- 「L4 外壳」的**窗口 / XAML / 消息循环 / 事件绑定**未实现；`src/QuadLite.App/` 里只有两个纯逻辑状态类型，不能启动、不能交互。
- 「此电脑 / 盘符由 `IDirSource` 合成条目、盘符按真实路径取图」只落地条目编排与图标策略判定，真实枚举与取图未接入。
- 「会话原子写 + `.bak` + `.bad-<时间戳>`」只落地读取侧字段归一与 `future-version` 拒读，写入侧属 Fs 层，未实现。
- 「接管冲突与进度 UI」仍是 `ADR-v2-004` D6 遗留项，未实现。
- 系统原生右键菜单属 B5，真实 `IFileOperation` 搬运、系统剪贴板互通、watcher 运行期仍属 B2 偏差，未实现 / 未验证。
- **本批不等于「应用可启动」**。B2 的 `ADR-v2-004` D6 把 WPF 外壳推给 B3；本批只把外壳的**可判定内核**与**可编译骨架**落地，§8.4「每批结束应用必须可启动」仍按 `ADR-v2-002` 的证据分层记为未达成，不宣称 MVP 可交付。

### D7（影响面）布局决策若改，替换边界已划清
若用户将来拍板采用自定义二叉分割树，需要替换的是 `LayoutMath` / `SplitMath` / `PaneSet` 的落位模型与 `ShellState` 的装配；`TabRules` / `NavRules` / `AddressRules` / `BookmarkRules` / `SessionRules` / `ThisPc` 与标签、导航、会话、书签门卡不受影响。同步要改的是 `design-v2.md` 的 FR-01 / §5.8 / 附录 C、`check_shell_specs.py` 的「规格与实现一致」门卡、以及 `layout-*` / `split-*` 门卡与负向对照。本批不预判结论，也不提前改规格。

## 理由

1. 用户明确「先按原计划开 B3」，而原计划即 `design-v2.md` §8.1 的 B3 定义；布局新方案尚在讨论，写进代码或规格都会替用户拍板，故按 v1.2 四档实现。
2. B3 门卡（`layout-*` / `split-*` / `tab-*` / `session-*` 等）全部是纯逻辑判据，可以在零 I/O 条件下 100% 单测；把不可在本机验证的 WPF 构建混进来只会稀释证据，与 B0–B2 的纪律一致。
3. App 层先落地「只读 Core 结果」的状态内核，既让 `src/QuadLite.App/` 不再是空目录，又保持依赖方向 L4 → L0 且零 I/O；真实窗口接入时不必推翻这批逻辑。
4. 把「规格与实现一致」做成门卡，是对上一轮越界的制度性兜底，而不是一次性道歉。
