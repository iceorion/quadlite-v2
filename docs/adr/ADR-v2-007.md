- **状态**：生效（2026-11-06）
- **批次**：B5（系统原生右键菜单：`NativeMenuHost` 薄壳、源头消重、参数硬校验、崩溃哨兵、自绘兜底）
- **关联**：`design-v2.md` §5.2 / §5.6 / §6.3 / §7.1 `menu-*` / §8.1 B5 / §10 / 附录 B / 附录 C；`ADR-v2-002` D5、`ADR-v2-004` D1/D6、`ADR-v2-005` D2/D7、`ADR-v2-006` D2/D6

## 决策

### D1（沿用）规格一字不改，布局决策继续挂起
`design-v2.md` 保持 **v1.2**。B5 的 `menu-*` 十条门卡、`FakeShellExtension` 四态与 B5 批次定义在 S3 就已在 §7.1 / §8.1 / 附录 C 登记，`check-trace` 天然绿，本批**不新增需求、不改规格**。用户提出的自定义分割线拓扑仍「讨论中、未定」，与 B5 无交集：B5 处理的是「一次右键会话如何安全地调用系统菜单」，布局处理的是「几个窗格、怎么摆」。

`check_menu_specs.py` 增加一条「规格与实现一致」门卡：规格 §8.1 的 B5 判据声明或 v1.2 状态被改动即判红，与 B3 / B4 的同名门卡并列，防止实现与规格静默漂移，也防止再次替用户拍板。

### D2（沿用 B1–B4 的证据分层）B5 交付可验证内核，不冒充可运行应用
| 层 | 内容 | 验证方式 | 结论 |
|---|---|---|---|

| L4 状态内核（App） | `MenuState` / `MenuCommands`：只读 Core 结果，装配宿主模式、会话态、ctxKey、safeListed、pending、TTL、maxId、快照计数与派发结果 | CI 编成 library（只编译、不运行）+ `check_menu_specs.py` 静态契约 | 结构与语法可判，运行期行为未验证 |
| 真实表现层 | `NativeMenuHost` / `IContextMenu` / `IContextMenu2`、`IContextMenu3` COM 调用点、`GetUIObjectOf` / `QueryContextMenu` / `TrackPopupMenuEx` / `InvokeCommand` / `HandleMenuMsg2`、HMENU 生命周期、`data\menu-pending.json` 磁盘标记、自绘兜底 UI、一键重试按钮 | B5 后续批次 / B6 / B7 / 发布线 | **未实现 / 未验证** |

本机安全策略禁止执行系统 C# 编译器，故本机只跑 Python 静态门卡；不把静态绿写成算法跑通，也不把 CI 编译写成应用可用。

### D3（关键语义纠偏）§5.2 的 `InvokeCommand` 范围只约束系统段
读规格时发现 B1 的 `MenuModel.IsValidInvokeId` 是**合并系统段与自有段**的 L0 通用判据；但 §5.2 明确规定自有命令 ID ≥ `0x8000` 走应用内派发，**不传给 `InvokeCommand`**，所以 `[1, maxId]` 的硬校验只针对系统段，不能套在自有段上。

处理方式是**不改 B1**（已验证行为契约沿用，DD-07），新建 `MenuInvokeRules`：

- `InvokeIdInRange(id, maxId)`：只判系统段 `id ∈ [1, 0x7FFF] ∧ id ≤ maxId ∧ !IsOwnId(id)`；
- `ShouldDrop(id, maxId)`：自有段返回 `false`，不因 `maxId` 被误丢；
- `Classify(id, maxId)`：先判 `MenuModel.IsOwnId(id)` → `Own`，再判系统段 → `System`，否则 `Dropped`；
- `OwnNeverLeaksToSystem` / `OwnSegmentDisjoint` 覆盖「自有项永不串到 shell」。

C# runner 的 `menu-own-id-segment` 组对此有专条断言，包含「shell 菜单为空时自有 ID 仍可派发」。

### D5（新增）CI 一步
`check-menu-specs`（B5 静态契约）。`csharp-runner` 与 `csharp-app-compile` 用目录 glob 自动包含 B5 新增的 8 个 Core 文件、2 个 App 文件与 `tests/QuadLite.Tests/MenuFakes.cs`，无需新增编译步骤：`csharp-runner` 编译运行 43 组，`csharp-app-compile` 把 Core + App（现 6 个 .cs）编成 library，只编译不运行、不引用呈现框架程序集。

### D6（偏差，如实登记）§8.1 B5 未交付完的部分
- **真实 `NativeMenuHost` 与全部 COM 调用点未实现**：`IContextMenu` / `IContextMenu2/3` / `GetUIObjectOf` / `QueryContextMenu` / `TrackPopupMenuEx` / `InvokeCommand` / `HandleMenuMsg2` / `DestroyMenu` 均无绑定代码。原因是 §5.2 禁止手写 COM vtable、而 O-01 的成熟绑定方案未定（与 `ADR-v2-004` D1 同源）。本批不改写这条约束，也不伪造绑定。
- **崩溃哨兵的磁盘侧未实现**：`data\menu-pending.json` 写入与清除、`menu-safe.json` 的 ctxKey 名单与 TTL 过期、`native-menu-degraded` 兜底 UI 与「一键重试」按钮都没有落盘或界面代码；`MenuState` 只装配这些状态的不可变内核，`HintText()` 返回结构化提示串。
- **`FakeShellExtension` 暂驻 Tests 层**：§6.3 把替身归在 `QuadLite.Probe`，本仓尚未建 Probe 项目；为避免 B5 引入空项目或让产品程序集引用测试替身，替身放在 `tests/QuadLite.Tests/MenuFakes.cs`，文件头已注明偏差，`check_menu_specs.py` 会检查产品程序集不引用 `QuadLite.Probe` / `QuadLite.Tests`。后续建 Probe 项目时迁移。
- **「单文件 / 免安装」只落地判据**：默认路径仍是单进程、零安装、免运行时；隔离宿主是可选演进项，本批只有 `OptionalHostIsOptIn()` 之类的规则，没有进程外宿主实现。
- **自有命令的 UI 挂点未实现**：源头消重与独立分组只落地 `MenuFusionRules.Resolve` 的纯函数判据，真实菜单项插入（自有段 ID ≥ `0x8000`）依赖 `QueryContextMenu` 宿主，未接入。
- **本批不等于「应用可启动」**，也**不宣称「原生菜单已可用 / 不再崩溃」**。§8.4「每批结束应用必须可启动」仍按 `ADR-v2-002` 的证据分层记为未达成。

### D7（影响面）布局决策若改，B5 不需返工
B5 的八个规则类型与两个状态内核只关心「一次右键会话」的宿主模式、ID 段、消息转发、目标快照、哨兵与释放，**不读窗格数量、不读落位模型**。若用户将来拍板采用自定义二叉分割树，替换边界仍是 `ADR-v2-005` D7 划定的 `LayoutMath` / `SplitMath` / `PaneSet` / `ShellState`。本批不预判结论，也不提前改规格。

## 理由

1. 用户「继续 B5」，原计划即 `design-v2.md` §8.1 的 B5 定义；布局新方案尚在讨论，写进代码或规格都会替用户拍板。
2. v1 崩溃根因是自造融合层逐项读 verb；B5 的十条门卡全部是可零 I/O 判定的结构与参数纪律，把不可在本机验证的 COM 混进来只会稀释证据，与 B0–B4 的纪律一致。
3. D3 的语义差异若直接改 B1，会破坏已验证的 L0 行为契约；新建专用规则类型并保留 B1 原义，是最小且可回归的做法。
4. 把「产品程序集 verb 查询 0 次」做成双重门卡 + 负向对照，是对 v1 事故最直接、可自动回归的制度性兜底。
