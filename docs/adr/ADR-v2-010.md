# ADR-v2-010：B8 发布线 C4 + H1–H6 规则层与发布记录状态内核

- **状态**：生效（2026-11-07）
- **批次**：B8（发布线 §8.3，§8.1）
- **关联**：`design-v2.md` §2.2 NFR-02/09/10/11、§4.3 DD-04、§5.11、§5.13、§7.3、§8.1 B8、§8.2、§8.3 发布线、§8.4 M3、§9 风险表、§10、附录 C F 组 / 非功能；`ADR-v2-008`（B6 布局拍板）、`ADR-v2-009`（B7 账本 / BUILD.txt / 预算表 / 崩溃摘要）

## 决策

### D1（沿用）布局保持 v1.2 四档，规格一字不改

用户对本批的指令是「继续 B8」。沿用 `ADR-v2-008` D1 的拍板：1/2/3/4 四档布局不变，自定义二叉分割树方案不采纳，`design-v2.md` 仍为 **v1.2**，FR-01 / §5.8 / §8.1 / §8.3 / 附录 C 未改。B8 属发布线 / 系统工程域，与窗格数量、落位模型无交集，`ADR-v2-005` D7 的替换边界不触发。新增的 `check_release_specs.py` 第 10 项继续核对规格版本、§8.1 B8 判据声明与 §8.3 降级路径原文。

### D2（沿用 B1–B7 的证据分层）B8 交付「可判定的发布线契约」，不冒充真实取证

| 层 | 内容 | 验证方式 | 结论 |
|---|---|---|---|
| L0 规则层（Core） | 新增 10 个零 I/O 类型：阶段链 / 证据等级纪律 / H1 DPI 四档 / H3 三段取证 / H2 兼容矩阵 / H4 崩溃读法 / H5 性能回归 / H6 OV 签名 / C4 零误报门槛 / M3 发布记录 | CI 以 `/langversion:5` 编译并运行零依赖 C# runner（71 组） | 规则算法实测（CI 远端） |
| L4 状态内核（App） | `ReleaseState`（阶段明细、降级链、当前 M3 判定）/ `ReleaseRecordState`（六阶段证据行、C4 声明、M3 verdict） | CI 编成 library（只编译）；runner 编译含 App 文件，故状态内核也被实跑断言 | 结构与语法可判，真实取证 I/O 未验证 |
| 真实发布线 | 高 DPI 四档截图与几何实测、注册表 / 应用目录 / 系统缓存三段取证、Win11 VM / LTSC × NTFS / exFAT / SMB / 只读载体八格实测、WER 读法、性能采样、OV 证书签名与指纹入库、C4 带杀软 VM | 需真实产品 exe + 真机 / VM + 证书 | **未实现 / 未验证** |

§8.3 明确「C4 缺位时按降级路径先做 H1 → H3 → H2，并在发布记录显式写『C4 未做』，不许用『没报错』冒充『没被拦』」。本批把这条纪律做成可判定规则：`AvScanRules.ZeroFalsePositiveClaimValid(engineCount, scanned)` 要求 `AVcount≠0` **且**实际扫描过；`EvidencePolicyRules` 复用 B7 账本四级证据等级，`Unverified` 一律不作判据；`ReleaseState.CurrentM3Verdict()` 把当前六阶段全部标为 `Unverified`，返回 `EvidenceMissing`，**明确当前 M3 不成立**——不把静态门卡全绿写成可发布。

### D3（§8.3 阶段链与降级路径逐项比对规格原文，不做常量自证）

`ReleaseStageRules.DependencyOrder()` 是 §8.3 代码块七节点顺序 `C4 → H1 → H3 → H2 → H4 → H5 → H6` 的可判定副本，`DegradedOrder()` 是降级链 `H1 → H3 → H2`。注意规格顺序**不是** H1→H2→H3：H3（零写入三段取证）在 H2（兼容矩阵）之前。

`check_release_specs.py` 第 5 项**解析 §8.3 原文**：从代码块提取 `└─ Hx` 链、DPI 四档数字、降级路径 `H1 → H3 → H2`，再与 C# 源码数组逐项比对（含顺序），任一项改名 / 改序 / 改数值都判红；负向对照 `spec-chain-drift` 把 §8.3 的 `└─ H3` 改成 `└─ H2` 即变红。`check-trace` 仍以规格文档为唯一权威，本副本不反向成为规格来源。

### D4（复用 B7，不重复定义已验证的常量）

B7 已落地 `EvidenceLevel` 四级、`BudgetTableRules` 四项七列、`CrashDigestRules` 五字段、`PackageSelfcheckRules.WriteEvidenceZoneCount()=3`、`BuildManifestRules.DirtyTreeWarning`。B8 的 `EvidencePolicyRules` / `PerfRegressionRules` / `CrashReportReadingRules` / `WriteEvidenceRules` / `CodeSigningRules` 一律委托这些类型，不另立第二套表。`check_release_specs.py` 第 4 项对 10 个文件的 38 项规格常量与不变量做静态核对，并显式要求几处委托存在，防止两批定义分叉。

### D5（H1–H6 的判据是可判定形态，不是真机结论）

本批门卡验证的是「每个阶段需要什么证据、证据等级如何才算数、矩阵缺一格是否判红、缺位是否显式声明、M3 是否能据此成立」，**不是**「四档 DPI 实测通过」「八格兼容实测通过」「OV 签名已完成」。`DpiMatrixRules.GeometryAssertionsPass(bool[,])`、`CompatibilityMatrixRules.MatrixComplete(bool[,])`、`PerfRegressionRules.RowComplete(string[])`、`ReleaseRecordRules.Evaluate(...)` 都是对传入观测数据的真判定（缺格 / 空值 / 未验证均判假），runner 对真、假两类输入都断言，避免退化成「`return true` 常量自证」。

### D6（偏差登记）M3 判据仍未达成，且这是批次路线的结构性结果

§8.4 定义 M3 = B8，判据是「发布线 H1–H6 逐项有证据；C4 缺位显式写『未做』」。本批交付的是发布线的**规则层 + 发布记录形态**，六阶段真实证据一项都没有，C4 带杀软 VM 未执行，C4 缺位也尚未在发布记录中显式声明（当前无发布记录）。因此 M3 **不成立**，`ReleaseState.IsPublishable()` 返回 `false`。

这与 `ADR-v2-005` / `ADR-v2-007` / `ADR-v2-008` / `ADR-v2-009` 登记的偏差同源：B2 起「批次完成」的含义一直是「可判定内核 + 门卡闭环 + runner 实跑」，而不是规格读者预期的「可运行 / 可发布产品」。根因仍是 O-01 成熟 COM 绑定未落地、真实 WPF 应用与单文件出包未接入。规格未改，本批不擅自插入「接真实实现」的批次。

## 理由

1. 用户明确「继续 B8」，并已确认保持四档、规格不改；本批不引入布局或规格返工。
2. H1–H6 规格定义的是**取证活动**，需真机 / VM / 证书 / 可运行 exe；把它们混进零 I/O 规则层会伪造证据等级，违反 §5.7 与 NFR-09。
3. 发布线最容易被「没报错」蒙混的正是 C4 零误报与签名链路；把 `AVcount≠0` 与「必须实际扫描」写成可判定函数，比在文档里写一句提醒更可靠。
4. 阶段链 H1→H3→H2 的顺序违反直觉，做成与 §8.3 原文逐项比对可防止后续实现按字母序悄悄改回去。
5. 复用 B7 常量表可避免同一份 4/7/5/3 在两批里各写一遍，这正是此前「门卡验证规格声明、未覆盖实现」漂移的成因。
