# ADR-v2-011：R1 真实实现第一批（单文件 WPF 宿主 / 产品 --selftest / 真实构建链）

- 状态：已接受（用户指令「开始接真实实现」）
- 批次：**R1**，规格 §8.1 之外的「实现批次」系列起点；规格 `design-v2.md` v1.2 **一字未改**
- 证据等级：本机 Python 门卡实测 / CI 远端编译与运行实测 / 未验证（逐项登记）
- 关联：`ADR-v2-001`…`ADR-v2-010`、`docs/run-ledger.md`、`docs/negative-controls.md`

## 背景

B0–B8 全部交付的是「可判定规则 + 状态内核 + 静态门卡」：Core 78 个零 I/O 类型、
Fs 5 个适配器、App 12 个状态类型、C# runner 71 组、Python 门卡 12 个、负向对照 63 条。
`README.md` 与 ADR-002/004/005/006/007/008/009/010 已如实写明 **M1 / M2 / M3 均不成立**：
没有可运行的 WPF 应用、没有真实 COM 绑定、没有单文件出包、没有产品 exe 形态的 `--selftest`。

用户在 B8 之后拍板开始接真实实现。本批只解决一件事：**让仓库第一次产出可编译、
可运行的真实 exe，并把它接进 CI 证据链**；真实 shell 能力按批次继续接。

## 决策

### D1 启用 R 系列，但不改规格

规格是「需求、架构、实现与验收的唯一规范」，§8.1 的批次表止于 B8 与「B8 之后（可选）」。
R 系列是**规格之外的实现推进**：补的是规格早已写明、但此前只落在规则层的能力，不新增需求、
不改 FR / NFR / 门卡组 / 四档布局。`check-realization-specs` 有一条断言明确禁止把 `R1`
写进规格 §8.1 批次表；`check-trace` 仍以规格附录 C 为唯一权威。

### D2 顺序调整：先做载体，再接 COM（修订上一轮口头提议）

上一轮提议的顺序是「COM 绑定 → 最小 WPF 窗口 → MSBuild 出包」。本批改为先做
「真实构建链 + 最小窗口 + 产品 `--selftest`」，理由：COM 绑定与出包都缺少可编译、
可运行的载体，先写进去只能得到「编译过」而拿不到任何运行证据，仍会退化为纸面。
**R2 接真实 COM 绑定（`IFileOperation` 托管互操作）与 Fs 真实 transport，R3 起接原生菜单宿主、
图标渲染与浏览 / 搬运 UI**。顺序调整不改变规格，也不改变「一次一处、每批可判定」的纪律。

### D3 技术选型：系统编译器一次编译四层源码 = 单 exe

`build.ps1` 用系统 .NET Framework 4.8 的 C# 编译器，以 `/target:winexe /langversion:5`
把 `QuadLite.Core` / `Fs` / `App` / `Host` 四层共 98 个 `.cs` **一次性编进一个程序集**，
显式引用 `PresentationFramework` / `PresentationCore` / `WindowsBase` / `System.Xaml`。
这样零 NuGet、零第三方合并工具（不需要 ILMerge / ILRepack）、零 XAML 编译任务，
天然满足「单 exe」；`src/QuadLite.Host/QuadLite.Host.csproj` 用同样的四层 `Compile Include`
表达 IDE 入口，MSBuild 出包路径**尚未实跑，标「未验证」**。
`app.manifest` 通过 `/win32manifest` 带入 PerMonitorV2（NFR-10），但四档真实截图仍属 H1，未做。

### D4 新增 Host 层，不改既有 App 层

真实窗口 / 入口放在新的 `src/QuadLite.Host/`，而不是塞进 `src/QuadLite.App/`：
既有 CI 的 `csharp-runner` / `csharp-app-compile` 会把 `App/*.cs` 编成只引用
`System.dll` / `System.Core.dll` 的 library，塞入 WPF 类型会直接判红；B3–B8 的门卡
还要求「App 状态内核零 I/O、不引用呈现框架」。新增独立层使 **既有 15 步 CI 与 12 个
Python 门卡的编译输入零改动**，风险最低。Host 层自身受新门卡约束：零 `System.IO`、
零手写 COM、零 verb 查询、零网络、C# 5 语法子集。

### D5 产品 `--selftest` 真跑断言，诊断态不创建窗口

`SelftestRunner` 复用 B7 的 `SelftestState.DetailLines()` 与 `SelftestReportRules`，
输出门卡总表 / 预算表 / 发布线 / 布局四档等明细，并**在运行时真跑 10 组 Core 契约断言**
（CLI 已知 / 未知参数、诊断态单实例豁免、四档布局、门卡总表、报告判据、BUILD.txt 字段、
M3 证据判定等）。报告 ≥100 行、末行 `verdict:`、退出码 = 红条数。
`--selftest` / `--diagnose` / `--shot` / `--shell-menu-host` 均不创建窗口，
CI 可在无交互桌面上实跑；诊断装置本身仍未接入真实设备，输出「未实现 / 未验证」。

### D6 单实例只落地第一段

`Program.Main` 只接了 §5.13 三段机制的 Mutex 第一段；`run.lock` 与 `WM_COPYDATA('QL')`
转发仍未实现，窗口状态栏与 ADR 均如实标注。不把「Mutex 能判重」写成「单实例已完整」。

### D7 证据纪律

本机受执行策略与编译器调用限制，**不执行 C# 编译器**：真实 exe 的编译与
`--selftest` 退出码只以 GitHub Actions `windows-latest` 远端实测为准，本机只跑 Python 门卡。
CI 新增三步：`check-realization-specs`、`real-exe-build`、`real-exe-selftest`
（断言 ≥100 行 / 末行 `verdict: GREEN` / 退出码 0 / `BUILD.txt` 七字段齐）。
日志端点匿名 403 时沿用「步骤 `success` ⇒ 退出码 0」判据，不读日志原文、不推断。

## 偏差登记（未实现 / 未验证）

- **M1 仍不成立**：窗口只有四档槽位文字与状态栏，没有目录枚举、列表控件、七档视图、
  筛选、拖放、跨窗格搬运与撤销、系统原生右键菜单。
- **真实 shell 互操作未接入**：`IShellTransport` 仍无真实实现；`IFileOperation` 托管 COM
  绑定、`NativeMenuHost` / `IContextMenu`、`ProgressSink` 回调、剪贴板与 watcher 真实行为均未实现。
- **图标缩略图未渲染**：WIC 白名单、`IShellItemImageFactory`、后台 worker、LRU 介质仍是规则层。
- **诊断与发布线未取证**：`--shot` / `--bench` / `--dumpmenu` 只输出「未实现 / 未验证」；
  高 DPI 四档截图、零写入三段取证、兼容矩阵、WER、性能采样、OV 签名、C4 带杀软 VM 全未执行。
- **单实例后两段、会话 / 书签持久化、`data\` 配置读写**未实现；窗口不写任何配置。
- **MSBuild 出包路径未实跑**：`QuadLite.Host.csproj` 只是 IDE 入口；`build.ps1` 的 csc 路径由 CI 实测。
- **M2 / M3 仍不成立**：`ReleaseState.CurrentM3Verdict()` 明确返回 `EvidenceMissing`，
  `IsPublishable() == false`；本批的 CI 全绿只证明「真实 exe 能编译、能自测」，不证明产品可用或可发布。

## 证据与结论

- 本机：12 + 1 个 Python 门卡与 `run_tests.py`（89 组 / 76 条负向对照）逐项实测绿，见 `docs/run-ledger.md` R1 行。
- CI：run 号与 18 步结论在 push 后回填（功能提交 → 账本回填 → CI 结论回填，沿用 B6–B8 三段式）。
- 结论：**R1 只把「可运行的载体」接入证据闭环**，不是 MVP，也不是可发布版本。
