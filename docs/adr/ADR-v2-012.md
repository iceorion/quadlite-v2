# ADR-v2-012：R2 真实 `IFileOperation` 托管 COM 绑定与 Fs transport

- **状态**：生效（2026-11-15）
- **批次**：R2（规格外实现批次，`design-v2.md` v1.2 一字未改、四档布局不变）
- **关联**：`design-v2.md` §5.1 / §5.2 / §5.12 / §6.1 / §7.1 / §11 O-01；`ADR-v2-001` D3、`ADR-v2-004` D3/D6、`ADR-v2-011`；`docs/negative-controls.md`、`docs/run-ledger.md`

## 背景

R1 交出可编译、可自测的真实单文件 WPF exe，但 `IShellTransport` 仍无真实实现，产品依然「不能搬文件」。规格 §5.1 把字节搬运 / 回收站 / ACL / 跨卷 / 长路径全部交给系统 `IFileOperation`；§5.2 参数纪律要求「COM 声明使用成熟绑定，不手写 vtable」；§11 的 O-01 已按默认执行（各批次分别使用成熟绑定 + 参数硬校验）。`ADR-v2-004` D3 因此推迟声明接口布局，并让 `check_fs_specs.py` 一见 COM 声明就判红。

R2 的目标是把这条真实调用链接上，同时不破坏 B0–B8 与 R1 已成立的证据闭环。

## 决策

### D1（新增）SDK 逐字对应的托管声明，作为**明确偏差**登记

零 NuGet（C-04）+ net48 + C# 5 + 单 exe 约束下，.NET Framework **没有公开托管的 `IFileOperation` 绑定**，引入第三方绑定又直接违反 C-04。因此本批采用与本机 Windows SDK 10.0.19041.0 头文件逐字对应的 `[ComImport]` 声明，集中在一个白名单文件 `src/QuadLite.Fs/ShellComInterop.cs`：

- 权威来源：`um/ShObjIdl_core.h`、`um/ShObjIdl_core.idl`、`um/shellapi.h`（本机实测读取，不靠记忆）。
- `CLSID_FileOperation = 3ad05575-8857-4850-9277-11b85bdb8e09`
- `IID_IFileOperation = 947aab5f-0a5c-4c13-b4d6-4bf7836fc9f8`
- `IID_IFileOperationProgressSink = 04b0f1a7-9490-44bc-96e1-4296a31252e2`（常见误传值为 `...f1b7...`，已按 SDK 纠正）
- `IID_IShellItem = 43826d1e-e718-42ee-bc55-a1e261c37bfe`
- vtable 方法数：21 / 16 / 5，顺序由 `check_transport_specs.py` 逐项硬校验。
- `FOF_ALLOWUNDO 0x0040`、`FOF_WANTNUKEWARNING 0x4000`、`FOFX_ADDUNDORECORD 0x20000000`、`FOF_NO_UI = 0x0614`、`SIGDN_FILESYSPATH = 0x80058000`。

**这是相对 §5.2「成熟绑定」的偏差**，不改写规格、不宣称满足原条款，也不做函数指针运算 / 非安全代码块 / vtable 改写。全部方法保留 `PreserveSig` 的 HRESULT 返回，参数顺序由门卡锁定。若将来允许 NuGet 或系统级托管绑定，替换点只在 `IShellTransport` 实现，编排层与端口契约无需改动。

### D2（新增）分层 COM 口径，单点定义

`tools/com_policy.py` 是唯一口径来源：COM 声明**只允许**出现在白名单文件；其余层（Core / Fs 其他文件 / App / Host / Tests）保持零声明，且全产品禁止函数指针式 vtable、verb 查询与菜单删项。

修订 `check_fs_specs.py`（B2 的「零 COM 声明」改为分层口径）、`check_menu_specs.py` / `check_icon_specs.py` / `check_selftest_specs.py` / `check_release_specs.py`（产品级扫描豁免白名单文件的那一条）、`check_realization_specs.py` 与 `check_open_source.py` 的措辞与必需清单。B2 的 `hand-written-com` 负向对照**保留**：往 `ShellFileOperator.cs` 注入 `[ComImport]` 仍必红。

### D3（新增）真实 transport 的执行契约

`src/QuadLite.Fs/ShellTransport.cs` 是 `IShellTransport` 的首个真实实现：

- 参数硬校验复用 `OpPlanBuilder.TryBuild`；回调越界索引丢弃。
- 每次操作新建 `IFileOperation` 实例，flags 为实例级；在**独立 STA 线程**执行，不在 UI 线程调用 `PerformOperations`。
- `Advise` / `Unadvise` 成对，`ProgressSinkBridge` 把 16 个 shell 回调翻译成 `IProgressSink.OnItem` 与 `OpItem`；`PostDeleteItem` 用 `SIGDN_FILESYSPATH` 取回收站真实路径，拿不到则 `ActualTarget = null`（该步不入撤销栈）。
- 删除用 `FOF_ALLOWUNDO`，永久删除加 `FOF_WANTNUKEWARNING`；撤销动作自身不加 `FOFX_ADDUNDORECORD`（不对称写入）。
- `try-finally` 释放全部 RCW；`FOF_NO_UI` 阻止系统模态框抽走消息泵。
- **默认 `Enabled = false`**，只有显式 `Enable()` 才触碰 COM。CI 的无交互桌面与产品 `--selftest` 不会意外发起真实文件搬运。

### D4（新增）证据纪律：只编译，不运行

本机仍不执行 C# 编译器；CI 的 `csharp-fs-compile` 与 `real-exe-build` 只把新文件编译进 Fs 库 / 单 exe，`real-exe-selftest` 只跑**纯契约断言**（`ShellContractRules` 的纯函数与「默认关闭」判定），绝不实例化 COM 对象、绝不调用 `PerformOperations`。真实 shell 行为一律标「未验证」，需 H1–H6 在真机取证。

### D5（新增）门卡与负向对照

新增 `tools/check_transport_specs.py`（单一声明文件 / 分层零声明 / SDK GUID / vtable 顺序 / flags / STA 与生命周期 / 参数硬校验 / 默认关闭 / 构建链与 CI / 规格未改 / 证据文档 / C# 5 / 诚实标注）；`run_tests.py` 扩到 102 组 / 88 条负向对照（12 条 R2 负向逐条实测变红）；CI 新增 `check-transport-specs` 一步；`build.ps1` 四层源码计数由 98 更新为 100。

### D6（如实登记）M1 仍不成立

窗口仍只有四档槽位文字与状态栏，没有目录枚举、列表控件、拖放与搬运入口；transport 默认关闭；列表控件 / 拖放 / 系统原生菜单 COM 宿主 / 图标缩略图渲染 / 单实例后两段 / 崩溃哨兵 / STA 线程 Join 超时 / `data\` 配置读写 / MSBuild 出包 / H1–H6 / C4 全部未实现或未验证。`ReleaseState.IsPublishable() == false`，**M1 / M2 / M3 均不成立**。

## 偏差登记（未实现 / 未验证）

- **§5.2「成熟绑定」未满足**：见 D1，已按偏差登记，不改规格。
- **真实 shell 运行期行为未验证**：COM 可用性、vtable 调用、回调时序、回收站真实路径、取消与部分成功、冲突 / 进度 UI、系统剪贴板与 watcher 真实行为。
- **线程与健壮性未验证**：STA 线程 `Join()` 无超时、崩溃哨兵与 SEH 边界未接入；异常只映射为 `ShellUnavailable`，不宣称不会崩。
- **产品能力仍为零**：没有浏览 / 搬运 UI，transport 默认关闭，用户无法触发真实操作。
- **发布线全部未取证**：H1–H6、C4 带杀软 VM、OV 签名、兼容矩阵、性能采样一项未执行。

## 证据与结论

- 本机：十四个 Python 门卡 / 自测脚本（13 个 `check_*.py` + `run_tests.py`）逐项实测绿，`run_tests.py` 102 组 / 0 失败、88 条负向对照逐条变红，见 `docs/run-ledger.md` R2 行。
- CI：**首次实跑已通过**，run `43713387488`（push head `bbbe0e5`，含功能提交 `08e0b95` → 账本回填 `bbbe0e5` → 本次 CI 结论回填，沿用 B6–B8 / R1 三段式）。job `gates` 结论 `success`，十九个门卡 / 编译步骤逐项 `success`：`check-transport-specs` `success`；`csharp-fs-compile` `success` ⇒ 托管 COM 声明与 transport 编译通过；`real-exe-build` `success` ⇒ 四层 100 个 .cs 一次编成单 exe、`BUILD.txt` 七字段齐；`real-exe-selftest` `success` ⇒ 产品 `--selftest` 报告 ≥100 行、末行 `verdict: GREEN`、退出码 0。既有 B0–B8 / R1 的步骤也全部保持 `success`。CI 只编译不实例化 COM，运行期行为仍标「未验证」；日志端点匿名 403 时沿用「步骤 `success` ⇒ 退出码 0」判据，不读日志原文、不推断。
- 结论：**R2 只把「真实搬运的代码路径与可判定契约」接进证据闭环**，不等于能搬文件，更不等于 MVP 或可发布版本。
