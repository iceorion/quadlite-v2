# ADR-v2-014：R4 系统原生右键菜单 COM 宿主

- **状态**：生效（2026-11-16）
- **批次**：R4（规格外实现批次，`design-v2.md` v1.2 一字未改、四档布局不变）
- **关联**：`design-v2.md` §5.2 / §5.6 / §5.12 / §7.1 `menu-*` 十条 / §8.2；`ADR-v2-007`、`ADR-v2-012`、`ADR-v2-013` D1；`docs/negative-controls.md`、`docs/run-ledger.md`

## 背景

B5 只交付了系统原生菜单的零 I/O 规则层（Core 的八个 `Menu*` 类型 + App 的 `MenuState` / `MenuCommands` + `FakeShellExtension` 四态替身），真实 `IContextMenu` 从未接入。`ADR-v2-013` D1 把 R3 收敛为浏览 / 搬运 UI，并把菜单宿主明确留给 R4：它需要第二套 COM 声明（`IContextMenu` / `IContextMenu2/3` / `IShellFolder`）与 owner 窗口消息转发，与浏览链路正交。

R3 之后，晃晃在本机跑通 `build.ps1`（`dist/single/QuadLite.exe`，133,120 B，`BUILD.txt` 七字段齐）并人工测试了窗口；这第一次让「单 exe 可启动」有了本机产物实证，但**具体交互用例与结论未记录**，不写进证据链当作通过。

## 决策

### D1（新增）R4 范围：只做原生菜单 COM 宿主，图标缩略图仍留 R5

按 ADR-013 的批次表，R4 交付：

- Fs 层 `NativeMenuHost.cs`：标准四步 + 独立 STA + 自建 owner 窗口 + 五类消息转发 + try-finally 释放。
- `ShellComInterop.cs` 扩为两套 COM 声明共用的唯一白名单，并集中全部 Win32 入口。
- Host 层 `MenuCommands.cs` + `PaneView` 右键事件 + `MainWindow` 状态栏接线。
- `tools/check_menu_host_specs.py`、`ADR-014`、负向对照、CI 与产品 `--selftest`。

拖放、图标与缩略图渲染（R5）、七档视图与筛选、会话与书签、`run.lock` / `WM_COPYDATA`、`--shot` / `--bench` 诊断装置均不在本批。

### D2（沿用并扩展）唯一白名单 + SDK 逐字对应，verb 口径收成单点

第二套声明全部落在 `src/QuadLite.Fs/ShellComInterop.cs`，值取自本机 Windows SDK 10.0.19041.0 的 `um/ShObjIdl_core.h` 与 `um/winuser.h`：

| 接口 | IID | vtable 槽位（IUnknown 之后） |
|---|---|---|
| `IContextMenu` | `000214e4-0000-0000-c000-000000000046` | 3 |
| `IContextMenu2` | `000214f4-0000-0000-c000-000000000046` | 4 |
| `IContextMenu3` | `bcfce0a0-ec17-11d0-8d10-00a0c90f2719` | 5 |
| `IShellFolder` | `000214e6-0000-0000-c000-000000000046` | 10 |

三个菜单接口各自列出 IUnknown 之后的全部槽位（CLR 按声明顺序映射 vtable），不做函数指针运算、不改写 vtable、不用非安全代码块。`tools/com_policy.py` 的 `EXPECTED_IDS` / `EXPECTED_METHODS` 扩到 R4 四段，由 `check-transport-specs` 与 `check-menu-host-specs` 同时逐项硬校验。

**口径修订（必须登记）**：SDK 第三槽的方法名必须出现在白名单的声明里，而 B-04 / B5 以来所有门卡把该字面量一律判红。R4 把判据统一到 `com_policy.verb_hit()` 单点：白名单文件允许 **SDK vtable 声明**、任何调用形态 `.MethodName(` 仍然判红；其余层出现方法名即判红。改用到该口径的有 `check-boundaries`（B-04）、`check-fs-specs`、`check-menu-specs`、`check-transport-specs`、`check-selftest-specs`、`check-release-specs`、`check_open_source` 共七处，判据精神未放宽：产品路径的 verb 查询次数仍为 0。

`§5.2「COM 声明使用成熟绑定」`的偏差继续沿用 ADR-012 的登记：零 NuGet + net48 下没有公开托管绑定，只能逐字对应 SDK 头文件，本批不修该偏差。

### D3（新增）标准四步与参数硬校验

每次右键新建菜单对象，在独立 STA 线程里执行：

1. `SHGetDesktopFolder` → `ParseDisplayName`（目录）→ `BindToObject`（父 `IShellFolder`）→ 逐项 `ParseDisplayName` 取子 PIDL → `GetUIObjectOf(IContextMenu)`。
2. `CreatePopupMenu` → `QueryContextMenu(idCmdFirst=1, idCmdLast=0x7FFF, CMF_EXPLORE|CMF_CANRENAME|CMF_ITEMMENU)` → `maxId = 返回值低 16 位 - 1`（走 `MenuInvokeRules.MaxIdFromQueryResult`）。
3. 自有项经 `MenuFusionRules.Resolve` 源头消重后，以**一条分隔线**独立成组追加，ID 从 `MenuModel.OwnIdBase = 0x8000` 起；`TrackPopupMenuEx(TPM_RETURNCMD|TPM_RIGHTBUTTON)` 期间由 owner 窗口转发消息。
4. 选中：`ID ≥ 0x8000` → 自有派发（只认打开右键那一刻的 `MenuTarget` 快照，不调 `InvokeCommand`）；`ID < 0x8000` → 先过 `MenuInvokeRules.InvokeIdInRange` / `Classify` / `ShouldDrop`，越界丢弃，合法才算 `InvokeOffset(id - 1)` 并调 `InvokeCommand`。

产品路径 0 次 verb 查询、0 次删项、0 次菜单树改写；`lpVerb` 用 MAKEINTRESOURCE 形态的偏移值，不读 verb 字符串。

### D4（新增）owner 窗口只转发五类消息，且只在会话内

`RegisterClassEx` + `CreateWindowEx` 自建隐藏 owner 窗口；窗口过程用委托字段由运行时封送（不取函数指针，遵守 `com_policy.RAW_VTABLE`）。`WM_INITMENUPOPUP` / `WM_DRAWITEM` / `WM_MEASUREITEM` / `WM_MENUSELECT` / `WM_COMMAND` 五类按 `MenuMessageRules.MustForward` 判定，优先 `IContextMenu3::HandleMenuMsg2`，无 3 则退回 `IContextMenu2::HandleMenuMsg`；其它消息交 `DefWindowProc`。菜单接口只在跟踪期间挂在静态字段上，会话结束立刻清空，不跨会话缓存指针。

### D5（新增）默认关闭 = 明确偏差，绝不冒充成功

沿用 R2/R3 纪律：`NativeMenuHost.Enabled` 默认 `false`，Host 层**不提供任何启用入口**；右键只回「菜单未执行：原生菜单宿主默认关闭（未启用 / 未验证）」，状态栏常驻 `native-menu=wired but disabled by default / 未验证`。

这是与规格 §5.2「默认路径 = 系统原生菜单」的**明确偏差**，理由：L3 崩溃哨兵（磁盘标记 / 按 ctxKey 降级 / 一键重试 / TTL 延长）与自绘兜底 UI 尚未实现，第三方 shell 扩展一旦在标准序列中异常会直接带走主进程；H1–H6 真机取证与 C4 带杀软 VM 也未开始。启用时机放到哨兵与取证之后，不在本批偷偷打开。

### D6（新增）门卡、负向对照、CI 与构建链

新增 `tools/check_menu_host_specs.py`（交付物 / 白名单 COM / SDK GUID 与 vtable / 零 verb 与零删项 / 标准四步 / 参数硬校验 / 自有项分组 / 消息转发 / 快照 / try-finally 与 STA / Host 接线与分层 C# 5 / 构建 CI / 规格未改 / selftest 与证据，共 16 组判据）。`run_tests.py` 增该门卡正样本与 R4 负向对照；CI 增 `check-menu-host-specs`；`SelftestRunner.cs` 增 8 组 R4 契约断言（仍不创建窗口、不实例化 COM）；`QuadLite.Host.csproj` 纳入 `MenuCommands.cs`；`build.ps1` 四层源码计数 103 → 105。

另修 `build.ps1` 的 UTF-8 BOM：本机 Windows PowerShell 5.1 按 GBK 解码无 BOM 脚本会导致中文注释解析错乱（第 110 行报意外 `}`），CI 用 pwsh 7 不受影响。本批把构建产物目录 `dist/` / `bin/` / `obj/` / `data/` 排除出开源扫描，避免本机 exe 让 `check_open_source` 在二进制上解码崩溃；`dist/` 本就在 `.gitignore` 里，不进仓。

### D7（如实登记）本机人工启动窗口

晃晃在本机跑通 `build.ps1` 并测试了 R3 窗口，产物 `dist/single/QuadLite.exe`（133,120 B，sha256 `58BD5D32…`，`BUILD.txt` 记录 `commit=3cac90a` / `worktree=dirty`）。这是「单 exe 可编译、可启动」的本机产物实证；但他未记录具体交互用例、四档渲染、目录枚举与搬运按钮的逐项结论，因此**真实交互仍标「未验证」**，不把「没报错」写成取证。`BUILD.txt` 的 `worktree=dirty` 来自 BOM 修复未提交，照实保留。

## 偏差登记（未实现 / 未验证）

- **§5.2 默认路径偏差**：宿主默认关闭，未启用时右键只回拒绝文案；启用需崩溃哨兵与真机取证完成后另议（D5）。
- **§5.2 成熟绑定偏差仍在**：SDK 逐字对应的托管声明未替换（D2）。
- **L3 崩溃哨兵 / 自绘兜底 / L4 隔离宿主**：磁盘标记、按 ctxKey 降级、一键重试、TTL 延长与 `--shell-menu-host` 全部未实现，运行期未验证。
- **读取菜单文本**：`GetMenuItemInfoW` 纯 Win32 读取路径未接入；源头消重只在自有项标签侧按 B5 规则完成，未与系统项文本实际比对。
- **真实 shell 运行期**：COM 可用性、PIDL / HMENU 生命周期、owner-draw 消息时序、`TrackPopupMenuEx` 模态循环、第三方扩展异常、多选项与空白面行为全部未验证；CI 只编译单 exe 并跑无窗口 `--selftest`，不开窗口、不枚举目录、不实例化 COM。
- **其余缺口**：拖放、图标缩略图渲染、七档视图与筛选、会话与书签、单实例后两段、`data\` 配置读写、MSBuild 出包路径、H1–H6 / C4 取证、真实 `IFileOperation` 运行期行为仍未实现或未验证。

## 证据与结论

- 本机：十五个 `check_*.py` 门卡（含新增 `check_menu_host_specs.py`）与 `run_tests.py` 负向对照逐项实测，结论见 `docs/run-ledger.md` R4 行；本机不执行 C# 编译器。
- CI：功能提交 → 账本 head_sha 回填 → push 后的 `gates` job 结论按步骤 `success` 回填；`real-exe-build` 编译四层 105 个 .cs，`real-exe-selftest` 跑产品 `--selftest`（≥100 行 / `verdict: GREEN` / 退出码 0）。**CI 结论待回填**。
- 结论：R4 第一次把系统原生菜单的标准四步、消息转发、参数硬校验与快照派发接进同一个单 exe，但宿主默认关闭、真实 shell 运行期完全未取证，**不等于 MVP，也不等于可发布版本**；M1 / M2 / M3 仍不成立。
